# B 구현 상세

## 1. 근거와 결정 범위

요구 동작은 최종 설계서 3-3(9~12쪽), 3-4(13~14쪽), 공통 타입(31~33쪽), RAG State(36쪽), 서브그래프/상한(39~44쪽), 구현 매핑(48쪽)을 따른다. 개발 절차는 최신 `DEVELOPMENT_RULES (2)(1).md`를 따른다. 강의자료는 구조 기반 분할과 출처 메타데이터의 참고 자료이며, 프로젝트가 제외한 Hybrid·Reranker·웹 자동 폴백을 다시 추가하는 근거로 사용하지 않았다.

설계가 특정하지 않은 저장 엔진은 B 내부 구현으로 SQLite+NumPy를 선택했다. 메타데이터 조건을 먼저 만족하는 후보만 모아 정규화 벡터의 내적으로 순위를 계산한다. 별도 서버·네트워크 API·추가 검색 모델은 없다. 이는 프로젝트용 exact Dense 기준선이지 대형 분산 벡터 검색 성능을 보장하는 구성은 아니다.

제공본의 본문 파싱·읽기 순서는 휴리스틱이다. 이 파일은 알고리즘의 구현 내용을 설명하며, 첨부되지 않은 여섯 논문을 모두 정확히 파싱했다는 보고서가 아니다.

## 2. 색인 파이프라인

```text
고정 manifest와 PDF 바이트 확인
  → 전체 PDF 페이지/200쪽 예산 확인
  → 텍스트 블록·좌표·서체·표 행·캡션·제외 구간 추출
  → 필요한 구조 검토 보완본의 승인/원문 해시 검증
  → Section/Subsection을 포함한 구조 블록 단위 처리
  → 400/600/800 논리 구간 확보
  → passage 접두어·특수 토큰·조건을 포함한 실제 입력 재분할
  → 모든 입력을 E5 tokenizer로 다시 검사
  → 고정 revision의 로컬 E5 masked mean + L2 정규화
  → 임베딩 캐시/SQLite 벡터·메타데이터 원자적 생성
```

### 2.1 원문 고정과 재현성

`Manifest`는 문서 ID, 판본, SHA256, 전체 페이지 수, 발행일, 서지 정보, 적용 기술/범위를 요구한다. 모델은 이름/40자리 revision/차원/입력 한도를 고정한다. 원문 SHA256을 확인하기 **전에** 기존 색인을 재사용하지 않는다.

색인 fingerprint는 manifest, 임베딩 정체성, 파서 버전, 청커 버전을 포함한다. 모델의 로컬 설치 위치·장치·배치 크기는 저장 경로나 처리 장비이므로 fingerprint에서 제외한다. 장비에 따른 미세한 부동소수점 차이까지 동일하다고 보장하는 것은 아니다. 원문·청킹·모델 정체성이 달라지면 새 색인으로 실행한다.

`DenseStore.create()`는 임시 DB 생성이 끝난 후 목적지로 publish한다. 이미 존재하는 경로를 덮어쓰지 않는다. 임베딩 캐시는 모델 정체성·query/passage 종류·원문 텍스트별로 분리한다. QueryLog·근거 ID·판정 결과를 임베딩 캐시에 저장하지 않는다.

### 2.2 PDF 파싱과 검토 보완본

`inspect_pdf()`는 PyMuPDF의 텍스트 블록과 좌표, 서체 크기/굵기, `find_tables()` 결과를 사용한다. 전체 폭 제목과 좌/우 단을 구분해 읽기 순서를 구성한다. 한 페이지에 단 구조가 충분히 드러나지 않으면 좌표 순서를 사용한다.

References 제목 이후 구간은 제외하고 Appendix 등 다음 상위 제목에서 본문 포함을 재개한다. 반복 머리말/꼬리말은 동일 위치 유형의 텍스트가 나타난 **서로 다른 페이지 수**를 기준으로 판단한다. 페이지 번호와 제목은 본문 임베딩 대신 제외/메타데이터 기록으로 보존한다.

표는 감지된 셀을 행 문자열로 만들고 헤더·캡션을 연결한 초안을 남긴다. 셀 병합이나 누락 단위를 추측하지 않는다. 표와 그림 캡션을 발견하면 검토를 요구한다. 이미지의 위치는 남기지만 픽셀로부터 수치/주장을 만들어내지 않는다. 그림 캡션만 있고 본문 설명이 떨어져 있으면 사람이 연결해야 한다.

`load_reviewed_structure()`는 원본을 덮어쓰는 대신 전체 승인 구조 보완본을 읽는다. PDF SHA/파서 버전/보완본 SHA, 검토자/시점/근거, block ID 중복, 페이지/좌표 범위를 검사한다. 표·그림에는 검토한 문맥을 요구한다. 형식적으로 `approved`라고 적었다는 사실이 의미 검토를 대신하지는 않는다.

### 2.3 구조 기반 청킹

`chunk_blocks()`는 파서 또는 승인 보완본의 구조 블록을 경계로 사용한다. 본문 문단을 무조건 합쳐 한 Section 전체를 단일 문자열로 만들지 않는다. 따라서 짧은 문단으로 이루어진 문서는 400/600/800 후보 간 청크 구성이 비슷할 수 있다. 청크 크기 후보를 실제로 비교해야 하는 이유다.

논리 구간은 E5의 raw token 수로 제한하고, 실제 입력은 section 경로·캡션/조건·passage 접두어·특수 토큰을 모두 포함해 목표 크기 이내로 나눈다. `split_ranges()`는 큰 구분자에서 작은 구분자로 경계를 선택하고 최종 부분 문자열의 토큰 수를 다시 확인한다. 한국어를 바이트 단위로 자르거나 토큰 ID를 다시 decode해서 원문을 바꾸지 않는다. 추적 위치는 파싱·정규화된 블록 내 문자 offset이며, 원본 PDF의 문자 바이트 offset을 의미하지 않는다.

60토큰 overlap은 같은 연속 텍스트의 실제 재분할에서 사용한다. 논리 구간·서로 다른 블록·다른 Section 사이에 강제 overlap을 넣지 않는다. 표는 제목·헤더·조건을 반복하고 행 경계를 우선한다. 행 하나와 문맥만으로 한도를 넘으면 추가 구조 검토를 요구한다. 긴 조건을 버리거나 수치만 남기는 자동 잘림은 없다.

### 2.4 저장 메타데이터

| 묶음 | 필드 |
|---|---|
| 원문 정체성 | source_key, version, source_sha256, date, ref |
| 위치 | page, locator, section, block_id, bbox, start/end |
| 청킹 | logical_start/end, logical_tokens, embedding_tokens, kind |
| 텍스트 | body, context, text |
| 적용 범위 | scope_by_tech, self_reported |
| 검색 | chunk_id, 정규화 벡터 |

`source_key`는 페이지가 아닌 문서 단위이다. 페이지/청크 정보는 `locator`에 있다. 같은 논문에 대한 `origin_key`는 source_key와 같다. 참고문헌 및 독립 출처 집계는 B가 별도로 늘리지 않는다.

문서 단위 direct로 지정했더라도 Related Work/Background 구간은 기본적으로 category로 낮춘다. 승인 manifest의 section별 범위로 보완할 수 있다. 검색 이후 선택한 claim도 범주를 확인하며, category를 direct로 올리는 LLM 출력은 거부한다. 단순히 기술명이 등장했다는 이유로 다른 시스템의 성과를 direct로 만들지 않도록 프롬프트에 명시했다.

## 3. 검색과 서브그래프

### 3.1 Metadata Filter → Dense 검색

`SearchFilters`는 비어 있지 않은 문서 ID와 scope allow-list를 요구한다. SQL에서 문서 ID·질의 기술의 적용 가능성·scope를 함께 검사한 후 벡터 내적을 계산한다. 공용 도메인 문서는 두 기술의 `scope_by_tech`에 category로 지정하므로 기술 필터 때문에 빠지지 않는다.

순위는 정규화 벡터 내적의 내림차순, 동점이면 안정적인 청크 ID 순이다. 벡터가 NaN/Inf이거나 차원·정규화 조건이 어긋나면 오류를 반환한다. 검색 결과가 TOP_K=5 또는 필터를 위반하는 경우도 래퍼가 성공으로 받아들이지 않는다.

### 3.2 실제 흐름

```text
START → retrieve → grade_chunks → extract
                                 ├─ 충분 또는 재작성 한도 → END
                                 └─ 부족 → rewrite → retrieve
```

`grade_chunks`는 `binary_score=yes/no`만 구조화로 받고 관련 후보를 만든다. `extract`는 관련 후보에서 단일 주장과 조건을 담은 연속 원문 구절을 추출하고 실제 청크 포함 여부·scope·중복을 확인한 뒤 최종 grade를 쓴다. `grade`의 런타임 writer는 extract 하나다.

충분 기준은 **현재 검색 Top-5에서 중복을 제외한 관련 근거 2개 이상, 그중 direct 1개 이상**이다. exact 동일 본문·같은 원문 offset 포함 관계, 같은 블록에서 추출한 동일/포함 구절을 중복 제거한다. 서로 다른 구절로 표현된 의미상 동일 주장까지 결정론적으로 완벽히 판별하지는 않는다. 의미 중복·단일 주장·실험 조건의 충실도는 실제 원문 대조 검수 항목으로 남긴다.

추출 단계는 원문에 없는 수치나 요약 문장을 새로운 claim으로 출력하지 않게 하는 보수적 구현이다. 연속 구절에 포함되었다는 사실만으로 그 구절이 충분한 조건을 담았다는 의미 검증까지 끝난 것은 아니다. 문맥 보존은 구조 검토와 프롬프트 지시, 추후 원문 대조가 함께 담당한다.

### 3.3 Query Rewrite와 종료

재작성 LLM은 검색어/약어 목록만 반환한다. 코드가 원래 기술명·aspect·대칭 템플릿·사용자 질문을 유지한 채 이 단어들을 붙인다. 다른 비교 기술명, 태그, 줄바꿈, 과도하게 긴 단어, 변화 없는 질의, 512토큰 초과 질의를 거부한다. 필터와 round는 재작성 노드가 반환하지 않는다.

최초 검색 이후 최대 두 번 재작성한다. 충분한 검색에서는 현재 근거만 반환한다. 마지막까지 부족하면 이전 시도에서 확보한 관련 근거도 보존해 반환할 수 있지만, 여러 시도의 근거를 합쳐 sufficient로 승격하지 않는다. 부족 사유에는 마지막 관련/direct 수와 검색 실패 수를 남긴다. 아무 관련 근거도 없으면 evidence는 빈 목록이다. 웹 검색 호출 또는 자동 폴백 경로는 없다.

### 3.4 오류와 호출 기록

검색 오류는 한 논리 질의에서 최초+최대 두 번 물리 재시도를 수행한다. 백오프는 1초/2초이다. 끝내 실패하면 해당 QueryLog 한 건에 failed/0건을 기록하고 빈 검색 결과로 진행한다. 각 물리 시도·오류 타입·메시지는 별도 audit에 남긴다. 재작성으로 만든 질의는 별도의 논리 검색이므로 QueryLog도 별도이다.

LLM 오류는 검색 실패와 섞지 않는다. 노드가 예외를 삼키지 않고 LangGraph RetryPolicy가 처리한다. 총 시도 수는 `max_attempts=3`으로 해석했다. 공급자 SDK 재시도는 기본 팩토리에서 0으로 설정한다. 한 노드에서 여러 청크를 처리하다 실패하면 해당 노드의 성공한 청크 호출도 노드 재시도에서 반복될 수 있다. B의 검색 논리 상한과 LLM의 실제 요청 수는 서로 다른 집계다.

감사 로그 저장 실패는 운영 오류이다. 이를 성공한 검색으로 조용히 덮지 않는다. 운영자는 로그 경로 접근 권한과 디스크 공간도 확인해야 한다.

### 3.5 공통 State와 반환 계약

서브그래프는 `compile(checkpointer=False)`이며 호출마다 새 내부 State를 만든다. 외부로 전달하는 RagResult는 `evidence`, `grade`, `uncertainty`, `confidence` 네 키다. 충분하면 uncertainty/confidence는 None, 부족하면 이유 문자열/low이다. 개별 Evidence에 confidence를 추가하지 않는다.

QueryLog는 B 호출 함수가 자동 생성해 바깥 운반 객체로 반환한다. 에이전트는 이 실제 기록을 누적할 뿐 LLM에게 로그를 만들게 하지 않는다. 부모 State는 함수에서 직접 바꾸지 않는다.

## 4. Golden QA 평가

### 4.1 승인 게이트

사람 승인 상태·검토자·시점·answerable 여부가 없는 질문은 평가하지 않는다. 질문의 gold chunk가 현재 색인에 존재하는지, 문서/판본/원문 SHA/페이지가 같은지, 정답 구절이 청크에 존재하는지, 고정 필터로 검색 가능한지 확인한다. 색인 fingerprint가 달라지면 전체 라벨의 재검토를 요구한다.

production split에는 두 기술×7항목×두 언어의 커버리지를 요구하도록 구현했다. 이는 질문 수가 미정인 설계에 대해 제안한 B 평가 세트 구성이지, 설계서에서 56문항을 의무화했다는 뜻은 아니다. 번역 그룹의 split 분리는 코드로 검사하고 실제 의미 누출은 사람이 확인한다.

### 4.2 지표

정답 근거가 존재하는 질문 집합 Q에 대해:

```text
Hit Rate@5 = (상위 5개에 정답 청크가 하나 이상 있는 질문 수) / |Q|
MRR@5      = Σ(상위 5개 내 첫 정답 청크 순위의 역수; 없으면 0) / |Q|
```

복수 gold가 있으면 첫 정답 순위 하나만 사용한다. 빈 질문 집합은 0점 대신 `n=0, metric=null`이다. 최초 질의와 재작성 후 마지막 질의를 서로 다른 필드에 기록한다. 검색 실패는 정답 있는 질문에서 miss로 남으며, 처리 예외로 질문이 누락되면 전체 보고서를 failed_incomplete로 하고 부분 성공 평균을 표시하지 않는다.

답이 없는 질문은 Hit@5/MRR@5 분모에서 제외한다. 한 번 이상 검색이 성공했을 때 insufficient로 판정한 비율을 별도로 측정한다. 모든 검색이 failed인 것은 정보 부재의 적절한 인정으로 세지 않는다. 지표는 검색 품질이지 전체 보고서의 진실성 또는 답변 정확도 점수가 아니다.

### 4.3 시간과 자원

색인 결과에는 parse/청킹 시간, embedding/publish 시간, 총 시간, 프로세스 최대 RSS를 기록한다. RSS는 같은 프로세스의 high-water 값이며 모델만의 증분 메모리로 표현하지 않는다. Linux/macOS `resource` 모듈을 사용하므로 Windows 네이티브는 별도 호환 검증 대상이다.

검색 trace에는 query embedding 시간과 Dense 검색 시간, 임베딩 캐시 적중 여부를 분리한다. 같은 장비와 캐시 조건에서 비교해야 한다. 이 제공본에는 실제 논문/E5 측정 숫자가 없다.

## 5. 공개 API 확인 자료

설계 동작은 첨부 문서가 기준이다. 아래는 구현 API 형태를 확인한 공식 문서이며 새로운 서비스 기능의 근거로 사용하지 않았다. 조회일 2026-09-22.

- E5 모델 카드: https://huggingface.co/intfloat/multilingual-e5-base
- LangGraph 서브그래프: https://docs.langchain.com/oss/python/langgraph/use-subgraphs
- LangGraph RetryPolicy 소스: https://github.com/langchain-ai/langgraph/blob/main/libs/langgraph/langgraph/types.py
- LangChain 모델/구조화 출력/재시도 설정: https://docs.langchain.com/oss/python/langchain/models
- PyMuPDF 텍스트/좌표 처리: https://pymupdf.readthedocs.io/en/latest/recipes-text.html
- PyMuPDF Page/table API: https://pymupdf.readthedocs.io/en/latest/page.html

E5 공식 예제에 자동 truncation이 등장하더라도 본 프로젝트에서는 사용자 계약에 따라 사용하지 않는다. 실제 런타임 설치와 해당 버전의 실행 호환성은 별도 시험이 필요하다.
